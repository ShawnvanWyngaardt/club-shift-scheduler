# Code audit, 19 Nov 2026

A one-off quality audit of the whole repo, written with Ponytail's `ponytail-audit` rules: correct first, then safe, then works when several people use it at once, then tested, fast and lean. Every finding below has a real situation where it goes wrong. No code was changed. The prompt at the end turns this into work when you are ready.

Branch audited: `redesign/coordinator-views` at `5d1511c`. Tests at the time: 47 backend and 56 frontend, all passing.

## What this repo does

A web app for Dutch amateur sports clubs. The coordinator posts shifts. Members tick the ones they can do through a personal link. A greedy solver hands out the shifts fairly, using an append-only points ledger. FastAPI and SQLModel run the backend, with SQLite locally and Neon Postgres in production. Vue 3 runs the frontend, and Render serves both from one URL.

**Load assumed:** a handful of clubs, each with one or two coordinators and 10 to 100 members, plus anonymous visitors on the public demo. The URL is public, so anyone on the internet can call the API.

## Must fix

### 1. Anyone can fill the database, because creating a club has no limit
`backend/routers/clubs.py:47-49`, also `:63-67` and `:125-147`

- **What this is:** `POST /api/clubs` creates a real club and returns its coordinator token. No login is needed, by design.
- **Problem:** "Try the demo" stops at 200 demo clubs (`sandbox.py:126`), but this endpoint has no limit at all. A small script can call it in a loop. Each new club's token then lets the same script add unlimited members, and up to 26 shifts per call. The free Neon plan pauses the database when it runs out of storage or compute, and then the app stops working for every club.
- **Fix:** Copy the demo cap. Count real clubs created in the last hour and answer 503 above a fixed number, such as 20. Add a cap per club on members (such as 300) and on shifts (such as 1,000) in `add_member`, `add_shift` and `add_weekly_shifts`. That's about 15 lines with no new dependency, and one test per cap.
- **If we skip it:** one bored visitor can take the live demo down until the database is cleaned up by hand.

### 2. A future shift can be checked in, and the points can't be taken back
`backend/routers/outcomes.py:89-135`, `frontend/src/checkin.ts:25-49`

- **What this is:** Check-in marks each person on a shift as done or missed and writes a ledger entry. That entry is final. There is no undo.
- **Problem:** The API accepts check-ins for shifts that haven't started yet. That was left open on purpose so demo visitors can try the page (journal, 16 Nov: "The backend should refuse it later"). But it also applies to real clubs. Say a coordinator ticks next Saturday's bar shift in the "upcoming" section by mistake. The member gets 3 points for work they haven't done, and nobody can reassign that shift any more.
- **Fix:** In `record_outcomes` and `record_outcome`, answer 409 with "This shift hasn't started yet" when the shift starts in the future and `club.is_demo` is false. Demo clubs keep the current behaviour. The tests that mark future shifts done need a club with `is_demo=True` or a past shift. Hide the "upcoming" section on the Check-in page for non-demo clubs.
- **If we skip it:** one wrong tap puts points in the ledger for good, and you'd have to fix them in the database by hand.

## Should fix

### 3. Two publishes at the same moment can put too many people on a shift
`backend/routers/schedule.py:78-88` and `:136-157`, `backend/models.py:178-182`

- **What this is:** Publish reads the empty slots, runs the solver and saves the assignments. "Fill by hand" does the same for one slot.
- **Problem:** Both requests read and then write, with nothing in between to stop a second request. If two board members share the coordinator link and both press Publish within a second, each one sees the same empty slots and saves its own picks. A 2-person shift can end up with 4 people, possibly with the same person on it twice, and both get points at check-in. The disabled button only protects a single browser tab. The `assignment` table also allows `shift_id` and `member_id` to be empty (`NULL`), and nothing ever writes that.
- **Fix:** At the start of `publish_schedule` and `assign_by_hand`, lock the club row: `session.exec(select(Club).where(Club.id == club_id).with_for_update()).one()`. A lock makes a second request wait until the first one has finished. Postgres honours it, and SQLite already lets only one write happen at a time. Add one migration that makes both columns `NOT NULL` and adds a unique constraint on `(shift_id, member_id)`, so the database refuses a duplicate even if code gets it wrong later.
- **If we skip it:** it's rare at today's size, but when it happens, a shift is overbooked and the fairness points are wrong.

### 4. The tests can't catch a delete in the wrong order
`backend/tests/test_api.py:22-30`, `backend/tests/test_demo.py:16-30`

- **What this is:** Removing a member, a shift or an expired demo club deletes the child rows before their parents (`sandbox.py:100-109`, `clubs.py:150-166`, `clubs.py:230-239`).
- **Problem:** By default SQLite ignores foreign keys, the links between tables, and the tests use SQLite. If someone moves a delete line in `delete_club`, every test stays green. Postgres refuses the delete, and because `start_demo` clears expired demos first, every "Try the demo" click would then fail. The README already lists the SQLite/Postgres gap.
- **Fix:** Turn foreign keys on in the test database with an `event.listens_for(engine, "connect")` hook that runs `PRAGMA foreign_keys=ON`, which is about 4 lines. Move the two copies of the engine and client fixtures into one `tests/conftest.py` while you're at it. Add one test that publishes and checks in inside a demo, then expires it, so the delete runs on a club that has assignments.
- **If we skip it:** the next change to a delete can ship green and break the demo in production.

### 5. The single check-in endpoint is no longer used by the app
`backend/routers/outcomes.py:89-102`, `frontend/src/api.ts:184-189`

- **What this is:** `PATCH /api/assignments/{id}` records one outcome. Since the redesign, Check-in saves a whole shift at once with `POST /clubs/{id}/outcomes`.
- **Problem:** A search of the frontend finds no caller of `recordOutcome`. Only the tests use the PATCH endpoint, in 6 places. That's two ways to write the same ledger entry, and both need the rule from finding 2.
- **Fix:** Delete the endpoint and `coordinatorApi.recordOutcome`. Change the 6 test calls to the batch endpoint, perhaps through a small `check_in(client, id, status)` helper in the tests.
- **If we skip it:** an extra code path that has to stay in step with the real one.

### 6. "Find this in the club, or 404" is written three times
`backend/routers/schedule.py:121-125`, `backend/routers/clubs.py:97-99`, `backend/routers/clubs.py:37-44`

- **What this is:** `find_in_club` fetches a member, shift or shift type and checks that it belongs to the club.
- **Problem:** `get_shift_in_club` in `schedule.py` does the same thing for shifts. `add_shift` checks the shift type by hand. If the rule changes, for example to the wording of the error message, someone has to find all three.
- **Fix:** Move `find_in_club` into `dependencies.py` next to `get_club_or_404`. Use it in `schedule.py`, which means deleting `get_shift_in_club`, and in `add_shift`. That's about 8 fewer lines.
- **If we skip it:** small, but the copies will drift apart.

## Nice to have

### 7. A ledger line can show the wrong day for a shift just after midnight
`backend/routers/outcomes.py:84`

- **What this is:** The ledger reason reads like "done: Bar, Sat 21 Nov".
- **Problem:** The date comes from the UTC time. A shift that starts at 00:30 Amsterdam time on Sunday 6 Dec is logged as "Sat 05 Dec". Most shifts are in the daytime, so this is rare.
- **Fix:** `f"{shift.starts_at.astimezone(CLUB_TZ):%a %d %b}"`, with `CLUB_TZ` imported from `sandbox`. One line.
- **If we skip it:** now and then a history line shows the day before.

### 8. Three API calls build the coordinator header by hand
`frontend/src/api.ts:200-214`

- **What this is:** Every coordinator call sends `X-Coordinator-Token` through `asCoordinator(token)`.
- **Problem:** `candidates`, `unassign` and `reassign` write the header out themselves, and `reassign` also repeats the `Content-Type` that `request` already sets.
- **Fix:** Use `asCoordinator(token)` there and drop the extra `Content-Type`.
- **If we skip it:** if the header name ever changes, someone has to edit four places instead of one.

### 9. Leftover and out-of-date bits
- `frontend/src/demo.ts:23`: a commented-out copy of `memberUrl`. The real one is in `links.ts`, so delete the line.
- `backend/routers/outcomes.py:50-58`: `require_changeable` repeats the status check in `require_no_outcome`. Have it call `require_no_outcome(assignment)` instead.
- `backend/routers/clubs.py:199-200`: the comment says SQLite returns times without a zone, but `UTCDateTime` returns them in UTC. Check the comment, and keep the SQL comparison either way.
- `README.md`: says "Python 3.12 or newer", but `backend/pyproject.toml` requires 3.13. The `description` field in `pyproject.toml` is still "Add your description here".
- Root `package.json`, `package-lock.json` and `neon.ts`: nothing in the app or CI uses them. They're settings for the Neon command-line tool. Keep them if you use `neon checkout` for branches, otherwise delete all three.

## Summary

**Verdict:** the code is healthy and well tested for its size. Fix 1 (open club creation) and 2 (future check-ins in real clubs) before inviting real clubs. Then do 3 and 4 together, because they share the database work.

**Lean:** about -50 lines and -2 root dependencies (`@neon/config`, `@neon/env`) possible.

**Not checked:**
- The Vue templates and styles in the large components (`WeekView.vue`, `ShiftList.vue`, `MemberList.vue`, the landing page). I read their logic files, not their markup.
- Accessibility and mobile layout.
- The Render config and the production database itself. Only the code was read.
- Behaviour on Postgres. The tests ran on SQLite.
- **Open question, not a bug:** a missed shift takes points away, which moves that person up the queue for the next shifts (journal, 17 Nov). That's a product decision, not a code fix.
